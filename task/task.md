# Migration & Feature Roadmap: Next.js, Trilingual i18n & Midtrans Payment

> **Status: ✅ Executed** — Vite + React SPA migrated to Next.js 16 (App Router) with
> English / Indonesian / Chinese routing and a full Midtrans Snap integration.
> `npm run build` passes; all three locales prerender as static HTML.
>
> **Before going live** you must fill in real Midtrans credentials — see
> [Remaining setup](#-remaining-setup-owner-action) at the bottom.

This document outlines the detailed execution task list for migrating the **Mountaint Jeep Sunrise** website from Vite + React SPA to Next.js, adding 3-language internationalization (English, Indonesian, Chinese), and integrating the Midtrans Payment Gateway.

---

## 📋 Task Overview

1. **Framework Migration**: Migrate Vite + React SPA to **Next.js (App Router)** for enhanced SEO and server-side rendering.
2. **Multilingual Support (3 Languages)**: Expand i18n support to **English (`en`)**, **Indonesian (`id`)**, and **Chinese (`zh`)**.
3. **Midtrans Payment Gateway**: Create server-side Midtrans integration (`lib/midtrans.js`), API routes for transaction token generation and webhooks/notifications.
4. **SEO & Performance Optimization**: Next.js Metadata API, `next/image` optimization, XML Sitemap, JSON-LD structured data, and responsive layout polish.

## 📊 Execution Results

### Stack
| | Before | After |
|---|---|---|
| Framework | Vite 5 + React 18 SPA | Next.js 16.2 (App Router, Turbopack) + React 19 |
| i18n | `react-i18next`, 2 languages, client-only | `next-intl` v4, 3 languages, SSG per locale |
| SEO | `react-helmet-async` (client-rendered) | Metadata API + JSON-LD (server-rendered) |
| Rendering | Empty HTML shell | Static HTML per locale (`/en`, `/id`, `/zh`) |

### Image optimization
The gallery originals are ~12 MP each and the hero was a 5.6 MB SVG. Served through
`next/image` (AVIF/WebP, responsive `sizes`):

| Asset | Before | After |
|---|---:|---:|
| Hero (LCP element), mobile | 5,698 KB | **12 KB** |
| Hero, desktop @1920 | 5,698 KB | **56 KB** |
| Gallery thumbnail | 916 KB | **30 KB** |
| Package card image | 470 KB | **16 KB** |

The hero was rasterized from `assets/hero.svg` to `public/hero.jpg`; the source SVG was moved
out of `public/` so it is no longer shipped. `public/og.jpg` (1200×630) was generated for social cards.

### Verified behaviour
- `/` → `307` → `/en`; `/en`, `/id`, `/zh` all `200` and prerendered.
- Language switcher swaps the route prefix and persists via the `NEXT_LOCALE` cookie.
- `robots.txt` and `sitemap.xml` serve correctly with a full hreflang cluster.
- JSON-LD emits 7 localized nodes (TravelAgency, TouristAttraction, WebSite, 4 × Product with IDR offers).
- Checkout rejects unknown packages, bad quantities, sub-minimum pax, malformed emails,
  past dates and missing tour types. **Prices are always resolved server-side — a client-supplied
  amount is ignored**, so the total cannot be tampered with.
- Webhook accepts correctly signed notifications (`settlement`→paid, `pending`→pending,
  `expire`→failed, `capture`+`challenge`→challenge) and rejects forged signatures with `403`.
- Zero console errors at 390 px, 820 px and 1440 px viewports.

## 🔑 Remaining setup (owner action)

1. **Add real Midtrans credentials.** `.env.local` currently holds placeholders, so live
   checkout returns `502 payment_gateway_error` by design. Copy `.env.local.example` to
   `.env.local` and paste the sandbox keys from
   Midtrans Dashboard → Settings → Access Keys. The Snap host (sandbox vs production) is
   derived automatically from the `SB-` prefix on the client key.
2. **Set `NEXT_PUBLIC_SITE_URL`** to the real domain before deploying — canonical URLs,
   hreflang, the sitemap, JSON-LD and the Midtrans finish-redirect all resolve against it.
3. **Register the webhook** in Midtrans Dashboard → Settings → Configuration →
   Payment Notification URL: `https://<your-domain>/api/midtrans/notification`.
4. **Run a sandbox test payment** end to end once the keys are in.
5. **Persist bookings.** There is no database in this repo, so the webhook currently logs
   settled bookings for manual reconciliation. The persistence hook is marked in
   `app/api/midtrans/notification/route.js` — wire an order store plus the confirmation
   email / WhatsApp message there.
6. **Run Lighthouse / PageSpeed Insights against the deployed URL** to record real-world
   scores (local numbers aren't representative of production CDN delivery).
7. **Refresh guest reviews periodically.** `data/reviews.js` is a manual snapshot and will
   go stale on its own — update the rating, count and entries from the Google listing every
   few months (steps in the README). If you ever obtain a Google Places API key, this
   section is the natural thing to make live.
